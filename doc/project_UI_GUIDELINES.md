# CareMemo UI設計ガイドライン (UI_GUIDELINES.md)

- このドキュメントでは、CareMemo の UI/UX 設計、および画面デザインの共通ルールを定義します。
- 具体的なファイル構成やコンポーネントの依存関係については、`project_structure.md` を参照してください。
- ソースコードを修正・追加・レビューする際の行動規範と実装ルールについては、`project_RULES.md` を参照してください。

---

# 1. UI設計思想

CareMemo では、画面を単なるテーブル単位ではなく「ユーザーの振る舞い」に基づいて設計します。

- **(A) 数値時系列**: 血圧、体重、血糖値など、推移をグラフ化し、推移を確認するもの。
- **(B) テキスト時系列**: 所見メモ、写真など、日常の出来事を時系列で記述するもの。
- **(C) 状態マトリックス**: データの入力日時に加え、 「データの持つべき日時 × データの状態」をマトリックスで管理するもの。
  - 例：**服薬管理** ･･･ 記録の入力・更新日時＋「服薬した日付 x (朝|昼|夕|寝る前) x (未服用・介助・服用)」

新規画面の追加時は、既存のいずれの振る舞いに該当するかをまず検討してください。

# 3. 入力・編集体験の統一 (AppTextField)

- アプリ内での数値・テキスト入力には、標準の `OutlinedTextField` を直接使用せず、必ずプロジェクト共通基盤である `AppTextField`（またはそれをラップしたコンポーネント）を使用して、入力体験（UX）を統一してください。
- CareMemo では、以下の挙動を「アプリ標準ルール」として定義しています。

  - **タップ時のカーソル制御（最重要）**: 入力項目をタップ（フォーカス取得）した際、既存の値を保持したまま**カーソルを自動的に末尾に移動**させます。
  - **自動フォーカス移動**: 以下の条件下で、手動操作なしに次の入力項目へフォーカスをリレーします。
    - **最大桁数（maxLength）到達**: 年月日などの固定桁数入力時。
    - **IMEアクション（Next）**: キーボードの「次へ」押下時。
  - **入力属性（AppTextFieldType）による自動設定**: `type` 引数を指定するだけで、以下の設定が自動適用されます。
    - **利用可能なタイプ**: `TEXT`, `INTEGER`, `DECIMAL`, `PASSWORD`, `EMAIL`, `PHONE`
    - **キーボード**: タイプに適したモード（数値、日本語、英数等）が自動選択されます。
    - **入力制限**: 数値タイプの場合、数字以外の入力が自動的に弾かれます。
    - **IMEアクション**: 文脈に応じた最適なボタン（次へ、完了等）が設定されます。
  - **自動フォーカススクロール (BringIntoView)**: 項目をタップしてフォーカスが当たった際、その項目がキーボードに隠れないよう、可視領域（キーボードの上）まで自動的にスクロールされます。これにより、ユーザーは手動でスクロールすることなくスムーズに入力を継続できます。

## コンポーネントの使い分け

見た目（サイズ感）に応じて選択してください。どちらも内部で `AppTextField` のロジックを継承しています。

| コンポーネント名                  | 用途                      | 配置場所                          |
|:--------------------------|:------------------------|:------------------------------|
| **`AppTextField`**        | 標準的な入力項目（名前、メモ、記録者など）   | `base/AppTextField.kt`        |
| **`AppCompactTextField`** | 省スペースが必要な数値入力（日時、バイタル等） | `base/AppCompactTextField.kt` |

## 実装上のルール
-   **FocusRequester の原則禁止**:
    画面上の並び順に従った標準的な入力遷移（例：年→月→日）を実現するために、**呼び出し側で `FocusRequester` を手動管理しないでください。** `AppTextField` の自動フォーカス移動機能に任せることで、配線コードのないクリーンな宣言的 UI を維持してください。

-   **例外的な挙動**:
    検索窓など、タップ時に値をクリアした方が利便性が高い特殊なケースに限り、個別に挙動を上書きすることを許可します。その場合は、ソースコード内にその理由を明記してください。

# 4. アクションの統一(AppDialog.kt)

## 共通ダイアログ(AppDialog)
- アプリ内での意思決定や情報の通知には、標準の `AlertDialog` を直接使用せず、必ずプロジェクト共通基盤である `AppDialog` 系コンポーネントを使用して、ユーザーの視線誘導と操作の意図を明確にしてください。

## コンポーネントの使い分け
用途と必要なアクションの種類に応じて選択してください。

| コンポーネント名                     | 用途                      | アクション（ボタン）                |
|:-----------------------------|:------------------------|:--------------------------|
| **`AppInfoDialog`**          | 登録完了の報告、入力エラーの通知、情報の周知  | 「閉じる」のみ（通知・フィードバック用）      |
| **`AppDialog`**              | 意思決定（保存・破棄の確認）、複雑な設定・入力 | 「確定」と「キャンセル」（選択・入力用）      |
| **`AppDeleteConfirmDialog`** | データの削除、抹消などの破壊的な操作の最終確認 | 「削除(警告色)」と「キャンセル」（破壊的確認用） |

### 各コンポーネントの役割
- **`AppInfoDialog`**: ユーザーの操作に対する**結果の通知**や、システムからの**警告**を伝えるためのものです。選択肢（分岐）を持たないため、ユーザーは内容を確認して閉じるだけの最小限の操作で済みます。
- **`AppDialog`**: ユーザーに**判断**を仰ぐ、あるいはダイアログ内で追加の情報を入力してもらうための「器」です。汎用的なコンテナとして機能し、内部に `AppDialogContent` を配置することで自動スクロールやレイアウトの統一性を保ちます。

## ボタン配置と視覚効果

CareMemo では、誤操作を防止しつつ操作を加速させるため、以下の「ボタン配置と視覚効果のルール」を定義しています。
  
### ポジティブアクション（確定・実行）
- **配置**: ダイアログの**右下**に配置します。
- **スタイル**: 常に**塗りつぶしボタン**（`AppDialogConfirmButton`）を使用し、最も目立つようにします。
- **色分け（AppDialogActionType）**: 操作の性質に応じて、以下の3色を使い分けます。
  - **SAVE (Primary)**: データの保存、登録、情報の確定。テーマの主色を使用し、画面全体のトーンと統一する。
  - **DELETE (Error)**: データの削除、情報の破棄、完全抹消などの破壊的操作。警告を示す赤系を使用する。
  - **ACTION (Tertiary)**: PDF出力、外部送信、同期処理の実行など、新しい価値を生む処理。Primary とは異なるアクセント色を使用する。

### ネガティブアクション（キャンセル・戻る)

- **配置**: ダイアログの**左下**（ポジティブアクションの左）に配置します。
- **スタイル**: 常に**文字のみのボタン**（`AppDialogDismissButton`）を使用し、視覚的な重みを下げます。

# 5. コンテンツの自動スクロールとキーボード回避

入力や編集を伴う画面では、キーボードによって操作が妨げられないよう、以下のルールを適用します。

### キーボード表示時の挙動 (adjustResize)
- アプリ全体の設定として、キーボード表示時には画面（ウィンドウ）サイズを自動的に縮小（リサイズ）させます。これにより、画面の下端がキーボードの上端に合わせて持ち上がります。

### 画面レイアウトの構成ルール
- **imePadding の適用**:
  入力画面のルートコンテナ（`Scaffold` 内の `Box` や `Column` 等）には必ず `Modifier.imePadding()` を適用してください。これにより、キーボードの高さ分だけ自動的に内側に余白が作られ、最下部のアクションボタン（保存・キャンセル等）がキーボードのすぐ上に配置されるようになります。
- **スクロールとインジケータの必須化**:
  キーボード表示によって画面が狭くなった際、隠れたコンテンツにアクセスできるよう、入力画面は必ずスクロール可能（`verticalScroll` 等）にし、かつ `VerticalScrollIndicator` を配置して「隠れているコンテンツがあること」を視覚的に示してください。

### ダイアログ内でのスクロール (AppDialogContent)
- ダイアログ内のメッセージや入力項目は、必ず `AppDialogContent` でラップしてください。これにより、コンテンツが画面高さに収まらない場合に、自動的にスクロールバー（`VerticalScrollIndicator`）が表示され、かつタイトルとボタンエリアが固定された正しいレイアウトが維持されます。


# 6. 配色とプライバシー（マスキング）

CareMemo では、データの重要度を直感的に伝えつつ、複数のテーマに柔軟に対応するため、「判定」と「配色」の責務を完全に分離します。

## 配色アーキテクチャ（責務の分離）

- **判定（Mapper）**: `HealthDisplayMapper` 等の層が、ビジネスルールに基づき「表示文字列」と「警告レベル（`HealthAlertLevel`）」を決定します。この層では `Color` を直接扱いません。
- **配色（Theme）**: `ui/theme/HealthAlertColor.kt` 等の層が、レベルに基づき「現在のテーマに最適な色」を決定します。
- **UI表示**: UI コンポーネントは、Mapper が返したレベルに対して拡張関数 `getDisplayColor()` を呼び出し、テーマから色を取得して表示します。

## 状態の視覚的区別（4段階＋1ルール）

判定結果の重要度に応じて、以下の 4 レベル（＋非アクティブ）を使い分けます。

- **正常 (NORMAL)**: `onSurfaceVariant`（グレー系）。情報をミュートし、異常値が発生した際のシグナル（色）を際立たせます。
- **注意/予備群 (WARNING)**: オレンジ系。ライト/ダークモードそれぞれで視認性を調整した CareMemo 独自のセマンティックカラー。
- **異常/警告 (ALERT)**: `error`（赤系）。即座に注意や対処が必要な状態。
- **情報/低値 (INFO)**: 青系（シアン系）。低血圧や低体重など、警告（赤）や注意（橙）とは性質が異なる特記事項。
- **非アクティブ (NONE)**: `onSurface` の透過色。バイタルインジケーター等の「該当なし（Off）」の表現に使用。

## プライバシー保護

- **一貫したマスキングロジック**:
  - 氏名等の伏せ字処理は `Person` クラスの一元化されたロジック（`getMaskedName`, `getMaskedFurigana`）を必ず利用し、画面ごとに個別実装しない。
  - **漢字氏名**: 交互にマスク（例：山○　太○）。
  - **カナ氏名**: 2文字目以降をすべてマスク（例：ヤ○○　タ○○）。
- **PDFの機密性保持**: PDF出力は外部共有を前提とするため、アプリの設定（伏せ字ON/OFF）に関わらず、**常にマスキングを適用した状態で出力**すること。
