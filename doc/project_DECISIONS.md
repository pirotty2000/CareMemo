# アーキテクチャ決定記録 (Architectural Decisions)

本ドキュメントは、CareMemo プロジェクトにおける重要な技術選定や設計変更の背景（なぜそうしたのか）を記録します。

## 1. Room の主キーを UUID (String) へ変更した理由
- **衝突の防止**: オフライン環境でのデータ生成を主とするため、複数の端末からデータをインポート・統合した際に数値連番（Long）だと ID が衝突するリスクがあった。
- **分散生成の容易性**: データベースに書き込む前（ViewModel層や一時ファイル生成時）に一意の ID を確定できるため、写真のファイル名とレコード ID の紐付けなどが確実かつ容易になった。

## 2. 2ペイン構成 (Tablet/Landscape) を採用した理由
- **画面効率の最大化**: タブレットや折りたたみデバイスの広い画面を活かし、「一覧」と「詳細・入力」を同時に表示することで、ユーザーの画面遷移コスト（戻って開き直す手間）を劇的に削減するため。
- **モダンなアダプティブ対応**: スマートフォン、タブレット、折りたたみ端末など、多様な画面サイズに対応し、一貫した操作性を提供するため。

## 3. StateFlow への統一の理由
- **MVI アーキテクチャの標準化**: UI 状態を一元管理する `UiState` 形式と相性が良く、単一方向データフロー（UDF）を確実に実現するため。
- **ライフサイクルセーフ**: `collectAsStateWithLifecycle` と組み合わせることで、Compose の再コンポーズ最適化と、アプリ背景移行時のリソース消費抑制を高いレベルで両立させるため。
- **プラットフォーム非依存**: `logic` レイヤーなどの Pure Kotlin 部分でも扱いやすく、テスト容易性が高いため。

## 4. `derivedStateOf` を ViewModel (UiState) へ移動した理由
- **テスタビリティの確保**: 「保存ボタンの活性化判定」や「変更検知 (`isChanged`)」は重要な業務判断であり、UI を介さずにユニットテストで論理的な正当性を検証可能にする必要があった。
- **真実のソースの集約**: Composable 内にロジックが分散するのを防ぎ、UI を「State を表示し、Event を送るだけ」の純粋な表示層に保つため。
- **再コンポーズの安定化**: キーの指定ミスによる意図しないリセットや、ViewModel からの「値の逆流」による入力不具合を構造的に防ぐため。
- **[禁止事項]**: Composable 内で業務ロジックを実装してはならない。

## 5. `safeLaunch` を導入した理由
- **横断的関心事の自動化**: 「例外ハンドリング」「監査ログ（AuditLog）の記録」「ローディング表示の ON/OFF」という、すべての破壊的操作で必須となる定型処理をカプセル化し、記述漏れやバグを根絶するため。
- **堅牢なエラー通知**: 発生したエラーを `AppException` 体系に基づいて適切に分類し、ダイアログ表示と証跡記録をハンドラへ確実に委譲するため。

## 6. ViewModel と Composable の責務を分離した理由
- **関心の分離**: ViewModel を「表示状態の管理と意思決定（画面遷移の判断等）」、Composable を「UI の構築とイベントの通知」に特化させることで、コードの可読性と保守性を高めるため。
- **テスタビリティの向上**: 画面遷移（navController.navigate）を Composable から直接呼び出さず、ViewModel が `ViewEvent` を発行する形に一元化することで、複雑な業務シナリオに基づく遷移ロジックを Unit Test で検証可能にするため。
- **UI の純粋性 (Stateless化)**: 具体的なビジネスルール（入力が正しいか、何が変更されたか）を UI 層から排除し、UI を「受け取った状態を正確に描画する」だけの単純な層に保つため。
- **[禁止事項]**: `navController.navigate()` を Composable から直接呼び出してはならない。

## 7. safeLaunch の後にのみ画面遷移を実行する理由
- **処理の原子性 (Atomicity) の保証**: データの保存や更新がデータベースに確実に成功した後にのみ画面を閉じる（または遷移する）ことで、データの欠落や不整合を構造的に防ぐため。
- **失敗時のユーザー保護**: `safeLaunch` 内で例外（DBエラーやバリデーションエラー）が発生した場合、ブロックの最終行に記述された遷移イベント（`sendViewEvent`）は実行されない。これにより、「保存に失敗したのに前の画面に戻ってしまう」といった混乱を防ぎ、ユーザーが入力内容を修正して再試行できる機会を確保するため。
- **予測可能な状態遷移**: 非同期処理の完了、成功通知、および画面遷移の順序を厳格に固定することで、ライフサイクルをまたいだ競合や、戻り先画面での不完全なデータ表示（同期遅れ）を最小限に抑えるため。
- **[禁止事項]**: `safeLaunch` の外側で画面遷移を実行してはならない。

## 8. リポジトリ設計の標準化（親：分離、子：フラグ併用）の理由
- **責務の明確化**: リポジトリを「DB永続化と監査ログ記録の実行者」に徹しさせ、新規・更新の業務判断を ViewModel（または Logic）へ一元化するため。これにより、データ層がドメイン層の判定ロジック（IdLogic 等）に依存する「レイヤー逆転」を解消し、アーキテクチャの純粋性を高める。
- **監査ログとの親和性**: 子テーブル（記録系）において、ひとつの `save` メソッド内で「保存」と「適切な actionType (INSERT/UPDATE) のログ出力」をセットで完結させることで、コードの重複を防ぎ保守性を向上させるため。
- **安全性の確保**: 親テーブル（Person）については、業務上「新規作成」と「既存変更」の重みが異なるため、物理的にメソッドを分けることで誤操作（意図しない上書き）に対する構造的な防壁とするため。

| 分類                 | 基本方式                  | 理由                                             |
|:-------------------|:----------------------|:-----------------------------------------------|
| **Person (親テーブル)** | Insert / Update 分離    | 新規登録と既存情報変更を業務上明確に区別し、誤操作を防ぐ。                  |
| **各記録 (子テーブル)**    | `save(..., isUpdate)` | 新規追加・編集を同一保存ユースケースとして扱い、ログ出力を共通化。              |
| **Repository**     | DB永続化に専念              | 新規/更新の判定は上位層から明示的に受け取り、忖度（推測）しない。              |
| **ViewModel**      | 操作種別を決定               | UI状態・編集状態から `isUpdate` を決定し、Repository へ指示を出す。 |
| **IdLogic**        | 上位レイヤーで利用             | Repository からドメイン判定ロジックを排除し、テスタビリティを確保。        |

## 9. 電話番号整形ロジックを独立・統合した理由（UI/Logicの分離）
- **Single Source of Truth (SSOT) の確立**: 「入力中」を担う `VisualTransformation` と「一覧表示」を担う `Mapping` 層でロジックが重複していた。これを `PhoneLogic` (Pure Kotlin) に集約することで、0120/0800 等の特殊番号帯の判定不整合を根絶するため。
- **アーキテクチャ規約の遵守**: Compose に依存する `VisualTransformation` が `logic` パッケージに配置されている規約違反を解消するため、ロジックの核（判定・計算）を `logic/common` へ、UI 制御（カーソル位置等）を `ui/utils` へと明確に分離・配置した。
- **テスタビリティの最大化**: 複雑なハイフン挿入条件を純粋な Kotlin コード（PhoneLogic）として抽出することで、JUnit による高速な網羅テストを可能にし、開発者がエミュレータなしでロジックの正当性を瞬時に確信できるようにするため。
