# CareMemo テスト実施ガイドライン

本プロジェクトにおけるテストの分類と、それぞれの目的・役割を定義します。開発が進むにつれ、これらのテストを段階的に構築することで、品質の維持（デグレ防止）を図ります。

---

## 1. ロジック・データ層のテスト (Unit Test)
**「目に見えないところ」の検証**

- **対象:** 純粋なロジック、計算、データ変換、リポジトリ、ViewModel の内部状態。
- **場所:** `app/src/test/` (Local Unit Test)
- **目的:** 入力データに対して、期待される正しい出力（または状態）が返るかを検証する。
- **例:** 
    - 漢字氏名の交互マスキングロジック。
    - 生年月日からの年齢計算。
    - DB からのデータ取得・保存処理。

## 2. UI 層のコンポーネント・挙動テスト (Component / UI Test)
**「画面の見た目」と「タップ時の反応」の検証**

このカテゴリは、さらに以下の 2 つのレベルに分けて実施します。

### 2-A. コンポーネント単体テスト (MainScreenContent 等)
- **対象:** 画面のレイアウト、部品の表示・非表示、引数による見た目の変化。
- **検証内容:** 
    - データの有無による「空状態」「リスト表示」の切り替え。
    - 検索バー、ボタン、インデックスバーの配置と表示。
    - 特定のデータ（誕生日、記録バッジ）に応じたアイコンの表示。
- **メリット:** ViewModel を介さずデータを直接注入するため、特定のパターンを高速に網羅できる。

### 2-B. 画面全体の挙動結合テスト (MainScreen 本体等)
- **対象:** 画面（View）と「脳（ViewModel）」の連動。
- **検証内容:** 
    - ボタン操作によってスナックバーが表示されるか。
    - スナックバーの「元に戻す（Undo）」を押して、削除がキャンセルされるか。
    - ViewModel から発行されたイベントによってダイアログが表示されるか。
- **目的:** ユーザーの操作が正しくロジックに伝わり、画面全体として正しい反応を返すかを保証する。

## 3. 導線・遷移のテスト (Integration / E2E Test)
**「画面の遷移」と「アプリ全体の流れ」の検証**

- **対象:** 画面間の移動、複数の画面をまたいだデータの整合性。
- **検証内容:** 
    - 一覧画面から特定の利用者を選択し、詳細画面（健康記録など）へ正しく遷移するか。
    - 詳細画面で入力・保存した内容が、一覧画面に戻ったときに正しく反映されているか（バッジ更新など）。
- **目的:** ユーザーがアプリで行う一連のストーリーが途切れることなく機能することを保証する。

---

## テスト作成の基本ルール
- **デグレ防止のガードレール:** 主要なボタンや表示項目には `testTag` を付与し、UI 変更時に意図せず機能が消えることを防ぐ。
- **可視性の確保:** 開発中の UI テストでは、操作の合間に `Thread.sleep(2000)` を挟むなどして、エミュレータ上で動作を目視確認できる速度にする（安定後は調整可）。
- **仕様の明文化:** テストコード自体が「この画面はどう動くべきか」という生きた仕様書として機能するように記述する。

## 付録：詳細画面のテスト構造化ルール
詳細画面（健康記録、所見メモ、服薬管理など）が追加される際は、以下の「3層構造」に基づいてテストを構成し、抜け漏れを防ぐこと。

### 1. 詳細画面の3層構造とテスト区分
| 層              | 役割        | テスト区分             | 主な検証内容                     |
|:---------------|:----------|:------------------|:---------------------------|
| **上層：ヘッダー**    | 共通ナビゲーション | **COM-01〜03**     | 戻るボタン、利用者氏名・年齢、PDF出力。      |
| **中層：カテゴリバー**  | カテゴリ切り替え  | **COM-04**        | 現在のカテゴリ選択状態、他カテゴリへの遷移。     |
| **下層：個別コンテンツ** | 画面固有の機能   | **CP-xx / BH-xx** | ローディング、各レイアウト固有の表示、保存等の挙動。 |

### 2. テスト ID 命名規則
仕様書とテストコードの紐付けを容易にするため、以下のプレフィックスを使用する。
- **COM (Common):** 全詳細画面で共通のパーツ。
- **CP (Component):** 画面固有の表示状態（Stateless な表示確認）。
- **BH (Behavior):** ユーザー操作に対する反応（コールバックやダイアログ）。

### 3. マルチレイアウトの必須検証
- **スマホ版 (Phone):** 1カラム、あるいはモード切り替え（カレンダー/履歴等）の動作を検証する。
- **タブレット版 (Tablet):** 2カラム構成において、リストと詳細（またはグラフ等）が同時に表示・連動しているかを必ず検証する。
