# CareMemo ViewModel 構造改善計画 (project_TODO_ViewModel.md)

このドキュメントは、現状の ViewModel における「責務の集中」「肥大化」「状態管理の複雑化」を解消し、長期的な保守性とテスト容易性を向上させるための具体的な改善案をまとめたものです。

---

## 🎯 改善の目的
1. **ViewModel の軽量化**: UI 状態の管理とイベントハンドリング（UIとの仲介）に専念させる。
2. **ビジネスロジックの独立**: 「判定」「計算」ロジックを独立させ、UI に依存しないテストを可能にする。
3. **状態管理の堅牢化**: 状態更新の原子性を確保し、UI との状態不整合（Race Condition）を防ぐ。
4. **エラーハンドリングの一貫性**: 例外やキャンセル処理の記述を共通化し、異常系への耐性を高める。

---

## 🚀 改善ステップ

### フェーズ 1: ドメインロジックの抽出 (重要度: 高)
ViewModel 内の純粋なロジックを UseCase や Logic クラスに抽出します。
*   **対象**: `PersonEditViewModel` (和暦計算/日付判定), `BatchInputViewModel` (重複判定)
*   **効果**: ViewModel の行数削減、ロジックの再利用性向上。UnitTestがしやすい。かなり保守性があがる。

### フェーズ 2: UI 状態（UiState）の集約と原子性の確保 (重要度: 高)
散在する `MutableStateFlow` を一つの `UiState` データクラスに集約します。
*   **具体的ルール**:
    *   **1画面 1UiState**: `loading`, `error`, `data`, `isValid` 等をすべて一つのデータクラスに包含。
    *   **原子的な更新**: `_uiState.update { it.copy(...) }` を用い、一部だけが更新された不完全な状態を UI に見せない。
    *   **派生状態の定義**: `isValid` 等を `combine` で合成せず、`UiState` のプロパティ（または更新時の計算結果）として保持する。
*   **対象**: `BatchInputViewModel`, `PersonListViewModel`
*   **注意**: 保存しておく必要がある値と、毎回計算して良い値は、分けて考える。

### フェーズ 3: ＜少し慎重に＞UseCase 層の導入によるオーケストレーション (重要度: 中)
複数のリポジトリを跨ぐ処理フローを UseCase に隠蔽します。
*   **対象**: `BatchInputViewModel` (一括保存フロー), `PersonBaseViewModel` (基本情報+サマリー取得)
*   **効果**: ViewModel の依存関係（Repository の数）の削減。
*   **検討**: 今の規模なら、Repositoryが十分整理されているなら無理にUseCaseを入れなくても十分ではないか？

### フェーズ 4: 例外・キャンセル処理の標準化 (重要度: 高)
`BaseViewModel` の機能を活用し、全画面で一貫した異常系・中断処理を実現します。
*   **具体的ルール**:
    *   **エラーの峻別**:
        *   **業務エラー**: 入力不正や重複など。`UiState` のエラー状態または `UiEvent` で個別に通知し、ユーザーに具体的な対処を促す。
        *   **システム例外**: ネットワーク切断やDBクラッシュなど。`safeLaunch` の共通ハンドラ（`CoroutineErrorHandler`）でキャッチし、ログ記録と共通エラーUIを表示。
    *   **キャンセルの自動制御**: `loadPersonJob?.cancel()` のような手動管理を減らし、`safeCollect` 等に「既存の処理があればキャンセルして開始する」モード（RESTART）を検討。
    *   **重要処理の完遂**: 保存処理や監査ログ（AuditLog）の出力など、画面が閉じられても中断してはならない処理には `NonCancellable` コンテキストや、より長命な `CoroutineScope` の利用を検討する。

### フェーズ 5: 異常系テストの拡充 (重要度: 高)
正常系だけでなく、エラー発生時やキャンセル時の挙動をテストコードで担保します。
*   **チェックポイント**:
    *   [ ] 保存失敗時に適切なエラーメッセージが表示され、入力データが失われないか。
    *   [ ] 通信遅延中に画面を閉じた際、DB書き込みなどの重要処理が不完全な状態で終わっていないか。
    *   [ ] 連続タップや高速な画面遷移時に、古い非同期処理の結果が新しい状態を上書きしていないか。

### フェーズ 6: ＜まだ早い？＞記録項目の抽象化による拡張性の向上 (重要度: 中〜高)
新しい記録項目（カテゴリ）を追加する際の修正箇所を最小限に抑えるための構造へ移行します。
*   **具体的ルール**:
    *   **プラグイン構造**: `BatchInputViewModel` 内の if-else による項目判定を廃止し、共通インターフェースを持つ「記録項目プロセッサ」のリストで処理する構造を検討。
    *   **メタデータの活用**: 入力項目の定義（バリデーションルール、単位、表示名）をコードから分離、または宣言的に定義可能にする。
*   **対象**: `BatchInputViewModel`, `PersonHealthViewModel`
*   **検討**: カテゴリが固定(全部で5つ)なので、そこまで抽象化しなくても十分保守できるかも。

## 💡 設計原則 (CareMemo Principles)

### 状態管理 (State Management)
1.  **Single Source of Truth (SSOT)**: 画面の状態は唯一の `uiState: StateFlow<T>` からのみ供給される。
2.  **State vs Event**:
    *   **State**: 画面に表示され続けるもの（テキスト、リスト、ローディング状態）。
    *   **Event**: 一過性の動作（トースト、ダイアログ表示、画面遷移）。`SharedFlow` で管理。
3.  **ViewModel は「加工場」**: Repository から流れてくる「生データ」を、UI がそのまま表示できる「UI用データ」へ ViewModel 内で変換しきること。UI（Compose）側に複雑な判定ロジックを書かせない。

### 非同期・例外制御 (Concurrency & Error Handling)
1.  **Fail-Fast & User-Friendly**: 回復可能なエラーは早期に判定し、ユーザーに分かりやすく伝える。システム例外は共通基盤で堅牢に守る。
2.  **Latest Result Only**: 検索やロード処理は、常に「最新のリクエスト」の結果のみを反映させる。古い処理の残骸を残さない。
3.  **Critical Section Protection**: データの整合性を守るための書き込み処理は、ライフサイクルによる自動キャンセルから適切に保護する。

### 拡張性 (Extensibility)
1.  **Open-Closed Principle**: 新しい機能や項目を追加する際に、既存の ViewModel の中心的なロジックを修正することなく、「追加」だけで対応できる構造を目指す。
2.  **Composition over Conditional**: if-else や when による条件分岐を増やすのではなく、オブジェクトの合成（Composition）によって複雑な挙動を組み立てる。

## 🛠️ 推奨される進め方 (Execution Strategy)

最も安全かつ確実に改善を進めるため、以下の「3ステップ・ハイブリッド方式」を採用します。

### ステップ A: パイロットケースの完遂 (垂直立ち上げ)
*   **対象**: `PersonEditViewModel`
*   **内容**: フェーズ 1（ロジック抽出）および フェーズ 2（UiState集約）を集中的に実施。
*   **目的**: CareMemo における「ロジッククラス」と「UiState」の標準的な実装パターン（型）を確立する。

### ステップ B: 難所の攻略とアーキテクチャの確定
*   **対象**: `BatchInputViewModel`
*   **内容**: フェーズ 2（UiState集約）および フェーズ 3（UseCase導入）を実施。
*   **目的**: 最も複雑な画面で新構造が通用することを証明し、UseCase 層の設計を確定させる。

### ステップ C: 全体への横展開 (水平展開)
*   **対象**: 全ての ViewModel（`PersonListViewModel`, `PersonHealthViewModel` 等）
*   **内容**: ステップ A/B で確立した「型」を順次適用する。
*   **目的**: プロジェクト全体の構造を統一し、保守性を最大化する。

## 📂 対象ファイルと優先度

| ViewModel 名 | 優先度 | 主な課題 | 適用推奨フェーズ |
| :--- | :--- | :--- | :--- |
| `BatchInputViewModel` | 🔴 最高 | 個別 Flow が多すぎ、保存ロジックが複雑 | 1, 2, 3, 5 |
| `PersonEditViewModel` | 🔴 高 | ロジックの混入、派生状態の算出が複雑 | 1, 2, 5 |
| `PersonBaseViewModel` | 🟡 中 | 共通処理と独自処理の境界が曖昧 | 3, 4 |
| `PersonListViewModel` | 🔵 低 | フィルタリングロジックの整理 | 1, 2 |

> [!NOTE]
> 上記以外の ViewModel（`PersonHealthViewModel` 等）についても、これらの「パイロットケース」での改善成果を順次横展開し、最終的にはプロジェクト全体の ViewModel 構造を統一します。
