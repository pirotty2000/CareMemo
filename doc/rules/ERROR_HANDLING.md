# エラーハンドリングと監査ログ

## 1. 例外設計と通知の委譲

- **原則**: 業務ロジックの失敗やシステムエラーは、`AppException` をスローすることで基盤側に通知（ダイアログ表示）を委譲します。
- **ViewModel の責務**: 判定事実（Enum等）を UIリソース（R.string）に翻訳し、適切な例外を生成・スローします。
- **手動表示の制限**: `safeLaunch` ブロック内において、直接 `showError` を呼び出すことは避け、例外による一元管理を優先してください。

## 2. AppException の継承階層

発生したエラーの性質に応じて、以下の例外を使い分けてください。これにより、適切な `resultType` でのログ記録が保証されます。

- **`AppValidationException`**: バリデーション失敗、業務ルール違反（重複等）。
- **`AppIOException`**: ファイル入出力、外部接続エラー。
- **`AppDataException`**: データ整合性不備、データベースエラー。
- **`AppExternalException`**: 外部アプリ（カメラ等）との連携エラー。
- **`AppSecurityException`**: 生体認証失敗、権限不足。

## 3. 操作ログ (監査ログ) の記録

- **正常操作**: Repository 内で、成功した操作の証跡を自動記録します。
- **エラー記録**: 例外発生時、`safeLaunch` の `contextBuilder` で指定された情報を基に、ハンドラが自動的に記録します。
- **論理ガードの記録**: 重複ロードの防止（`GUARD_SKIPPED`）など、例外ではないが診断上重要な「意図的な中断」も記録してください。

## 4. 通知の使い分け

- **致命的・要対話エラー**: `AppException` をスローし、ダイアログで通知。
- **正常な完了通知**: `showSnackbar` を使用（保存完了、削除完了等）。
