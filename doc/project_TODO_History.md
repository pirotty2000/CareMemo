# CareMemo プロジェクト開発履歴 (History)

本ドキュメントは、プロジェクトの各フェーズにおいて「何が問題で」「何をしたのか」を振り返るための記録です。ロードマップやチェックリスト等の進行管理情報は除外し、設計判断と実施内容の要約を記載します。

## 2026/08/28: Phase 7 - 境界設計の洗練と実測ベースの性能最適化

### 概要
全 14 画面を対象とし、UI 構造を「Action Collection Pattern」へ移行。表示層の純粋化と Compose コンパイラ最適化を極限まで追求。

### 課題 (Problems)
- **結合度の増大と Callback Drilling**: 画面の多機能化に伴い、表示層（Content）へ渡されるコールバックが激増（多い画面で10個以上）し、保守性が低下していた。
- **Recomposition の不安定さ**: ViewModel や Navigator を参照する Lambda が unstable と判定され、無関係な State 更新時にも画面全体が再描画される性能上の懸念があった。
- **UI 制御ロジックの分散**: 削除確認や変更破棄警告などの副作用制御が Screen と Content に跨っており、バグの温床となっていた。

### 実施内容 (Actions)
- **Action Collection Pattern の全面採用**: 各画面に `UiAction` (Sealed Interface) を定義。検索、入力、遷移、ダイアログ操作などの全ユーザー操作を一つの `onAction` ラムダへ集約。
- **表示層の完全 Stateless 化**: 全ての Screen から `Content` コンポーネントを抽出し、`UiState` と `onAction` のみを受け取る構造へリファクタリング。
- **実測ベースの Lambda 安定化**: Compose Compiler Report の解析結果に基づき、全ての `handleAction` ラムダを `remember` で固定。内部で参照する最小限の状態プロパティ（`isChanged` 等）をキーに指定することで、正確かつ最小限の再生成を実現。
- **品質の網羅的検証**: リファクタリング後の全画面を対象に計 73 項目のインストルメンタルテストを実行し、機能の正常性と `testTag` 基盤を点検。
- **ドキュメント整備**: ADR #14 を新設し、UI 境界設計と最適化の標準指針を記録。

## 2026/08/23: Phase 7 - 状態管理の堅牢化と復元（SavedStateHandle）の徹底

### 概要
プロセス死（Process Death）からの完全復帰を目指し、プロジェクト全体の「状態」の定義と管理ルールを再構築。

### 課題 (Problems)
- **不完全な復元**: 入力中のテキストや検索クエリ、ダイアログの選択状態などがプロセス死で消失し、ユーザー体験を損なっていた。
- **基準値の不一致**: 編集中の「変更あり/なし」判定に使用する初期値が復元されず、復帰後に変更検知が正しく機能しなくなっていた。
- **状態定義の曖昧さ**: どこを ViewModel で持ち、どこを SSH に保存すべきかの境界が不明確だった。

### 実施内容 (Actions)
- **「CareMemo 状態管理 7 原則」の確立**: SSOT の維持、論理的一括復元、初期化上書き防止などの設計指針を定義。
- **Restorable State の全面実装**: 全主要画面において `SavedStateHandle` を用いたバックアップ・復元機構を実装。1文字も失わない入力保護を達成。
- **状態の 4 分類**: 画面の状態を UI/Restorable/Nav/Transient に厳格に分類し、設計の透明性を向上。

## 2026/08/22: Phase 6 - 監査ログの強化とエクスポート機能

### 概要
例外処理の可視化と、外部メンテナンス用のログ抽出機能の実装。

### 課題 (Problems)
- **隠れたエラーの黙殺**: ファイル操作や DB の自動再作成などの重要イベントが `try-catch` で握りつぶされ、証跡が残っていなかった。
- **ログの閉鎖性**: 監査ログがアプリ内の DB に閉じており、トラブルシューティング時に外部から確認できなかった。

### 実施内容 (Actions)
- **監査ログ・エクスポートの実装**: 監査ログを JSON および CSV 形式で出力し、パスワード付き ZIP としてエクスポートする機能を実装。
- **例外処理の再整理**: `Ignored` とされていた例外（IOエラー、DB再作成等）をキャッチし、監査ログに記録するよう修正。
- **SystemEmergencyLogger の新設**: DB が破損・ロックされている場合でも、ファイルシステムへ緊急ログを記録する仕組みを導入。

## 2026/08/21: Phase 5 - プロジェクト適合性調査

### 概要
全コンポーネントを対象としたルール適合状況の総点検と、発見された不整合の解消。

### 課題 (Problems)
- **監査ログの記録漏れ**: インポート操作や設定変更、物理削除失敗時のログが不足していた。
- **アーキテクチャ違反**: リポジトリが UI リソース (`R.string`) に依存したり、UI 部品が ViewModel に直接依存したりしていた。

### 実施内容 (Actions)
- **監査ログの網羅性向上**: 破壊的操作や重要設定の変更時における監査ログ記録を徹底。
- **UI リソース依存の解消**: `DatabaseInconsistency` 等の理由定義を UI リソースから切り離し、ドメインモデルとして定義。
- **UI コンポーネントの Stateless 化**: `PdfExportActionHandler` 等から ViewModel 依存を排除し、呼び出し側から制御する設計へリファクタリング。

## 2026/08/15: Phase 4 - アーキテクチャ境界の純粋化

### 概要
レイヤー間の依存関係ルール（Dependency Matrix）を厳格に適用し、モジュール間の結合度を低減。

### 課題 (Problems)
- **依存関係の逆転**: Repository が Logic に依存したり、ViewModel が Android Context を保持したりする規約違反が発生していた。
- **セキュリティ境界の甘さ**: アプリ起動時や重要操作時（データ出力）の認証チェックが不十分だった。

### 実施内容 (Actions)
- **プラットフォーム依存の排除**: ViewModel から `Context` や `BiometricManager` への直接参照を排除。
- **Repository の純粋化**: `AppMaintenanceRepository` 等から Logic への依存を排除し、永続化のみを担当する構造へ修正。
- **セキュリティ強化**: アプリ起動時のデフォルト・ロック、および PDF 出力等の重要操作時の再認証（Step-up Auth）を導入。

## 2026/08/14: Phase 3 - UI 境界の整合性と最適化

### 概要
UI と ViewModel の境界における責務を整理し、ビジネスロジックの漏れ出しを解消。

### 課題 (Problems)
- **責務の混在**: `derivedStateOf` を用いたビジネスロジック（変更検知やバリデーション）が Composable 内に存在し、テストが困難だった。
- **不変コレクションの過剰適用**: Logic レイヤーまで `ImmutableList` に依存しており、純粋なロジック層の柔軟性が損なわれていた。

### 実施内容 (Actions)
- **ロジックの ViewModel 集約**: `isChanged`（変更検知）やバリデーション判定を Composable から ViewModel へ移動。
- **UI 境界の整理**: `ImmutableList` への変換を ViewModel (UI境界) に限定。
- **テスト戦略の強化**: 画面遷移を跨ぐデータ整合性を検証するシナリオテストを整備。

## 2026/08/09: Phase 2 - 次世代品質向上プロジェクト (アーキテクチャ刷新)

### 概要
Jetpack Compose / Material 3 の最新ベストプラクティスに基づき、アプリの堅牢性と保守性を抜本的に高めるための基盤刷新を実施。

### 課題 (Problems)
- **脆弱なナビゲーション**: 文字列ベースのルート定義により、型安全性が欠如。
- **パフォーマンスの懸念**: リストの再コンポーズが最適化されていなかった。

### 実施内容 (Actions)
- **Type-safe Navigation の導入**: `@Serializable` なオブジェクトによる型安全な遷移へ移行。
- **不変コレクション (ImmutableList) の採用**: UI 状態の安定性を確保。
- **Modifier ルールの厳格化**: コンポーネントの予測可能性を高めるための伝播ルールを全画面に適用。

## 2026/07/20: Pre-Phase - ViewModel 構造改善計画の策定

### 概要
ViewModel の肥大化と状態管理の複雑化を解消するため、アーキテクチャの基本原則を再定義。

### 課題 (Problems)
- **ViewModel の責務過剰**: UI 状態の管理、イベントハンドリング、複雑なビジネスロジックが単一の ViewModel に集中していた。
- **拡張性の限界**: 新しい記録項目の追加時に大量の条件分岐が発生する構造だった。

### 実施内容 (Actions)
- **設計原則 (CareMemo Principles) の確立**: SSOT の徹底、State vs Event の分離、非同期制御の標準化。
