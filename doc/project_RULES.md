# 1. 設計思想

## 1.1. 設計思想

project_UI_GUIDELINES.mdの「UI設計思想」参照。

## 1.2. 詳細画面の設計原則 (A/B/C共通)

利用者詳細に紐づく主要3カテゴリ（健康記録・所見メモ・服薬管理）は、以下の原則に基づき構造が統一されています。

### 1.2.1. 構成ファイルの統一 (4ファイル構成)

各カテゴリは、原則として役割を分離した4つのファイルで構成されます（MainScreen等、現時点でマルチペインが不要な画面は Tablet/Phone を分けない場合がありますが、Content の分離は共通ルールとします）。

- `Screen.kt`: 画面のエントリポイント。WindowSize判定と各ViewModelの管理、および**画面遷移の実行（ViewEvent を受けて navController.navigate() を実行）**を担当。
- `ScreenPhone.kt`: スマートフォン用レイアウト。シングルペイン構成。
- `ScreenTablet.kt`: タブレット用レイアウト。2ペイン構成。
- `ScreenContent.kt`: Phone/Tabletで共有されるコアな表示・入力ロジックの定義（Stateless）。

### 1.2.2. ViewModel の二段構え (Dual-ViewModel)

すべての詳細画面 Composable は、以下の2つの ViewModel を併用します。

- **`PersonDetailUiStateViewModel`**: 詳細画面全体の共通フレームワーク（利用者基本情報の保持、カテゴリ切り替え、共通UIイベント等）を担当。
- **専門 ViewModel**: 各カテゴリ固有のデータ操作（CRUD）とビジネスロジックを担当。
  - (A) `PersonHealthViewModel`
  - (B) `PersonConditionViewModel`
  - (C) `PersonMedicationViewModel`
- **自律的な初期化と連携**: 各 ViewModel は、Type-safe Navigation によって `SavedStateHandle` に自動注入された引数（`personId` 等）を自ら取得し、自律的にデータロードを開始します。Screen (Composable) から手動で `loadPerson` をキックする必要はなく、システムによる自動初期化によって ViewModel が自己完結する構造を維持します。
- **非同期プロパティの初期値セット**: ユーザー設定（デフォルト記録者名等）のように非同期で取得される値を入力の初期値として使用する場合、`init` ブロック内での単純な `.value` 参照は避けること（初回取得が完了していない可能性があるため）。Flow を `collect` し、**「編集モード中で、かつ値が未入力の場合のみ自動で埋める」**といったリアクティブな補完ロジックを実装してください。

## 1.3. レイヤー別責務定義

プロジェクトの各レイヤーは、以下の原則に基づき独立した責務を負います。

| レイヤー / パッケージ                                    | 主要な役割（責務）                                                                                                      | 担当する「問い」                                   | 注意事項・禁止事項                                                                       |
|:------------------------------------------------|:---------------------------------------------------------------------------------------------------------------|:-------------------------------------------|:--------------------------------------------------------------------------------|
| **`data/AppSpecifications`**<br>(および `spec` 配下) | **数値の源泉**。ビジネスルール（閾値）、入力制限（桁数）、UI制約（写真枚数）などの定数を一元管理する「プロジェクトの辞書」。                                              | 「正常値の基準となる数値は何か？」「入力可能な最大文字数は？」            | **ロジック禁止**: 計算式や `if` による条件分岐を含めない。純粋な定数定義に徹する。                                 |
| **`logic/common`**                              | **ドメインルール（脳）**。数値に基づく「事実（Status）」や「深刻度（AlertLevel）」の判定を行う。Android非依存（Pure Kotlin）。                             | 「この数値は医学的にどの分類で、どの程度深刻か？」                  | **Android依存禁止**: `Context` や `R.string` 等を参照しない。「事実」としての Enum や結果型のみを返す。        |
| **`logic/feature`**                             | **機能ロジック**。画面の入力状態（UiState）からEntityへの変換、保存前の相関チェックなど、特定機能に閉じた純粋ロジック。                                           | 「この画面の入力内容は保存可能か？」「StateをどうEntityに詰め替えるか？」 | **副作用禁止**: リポジトリの直接呼び出しや、画面遷移・通知（UI操作）を内部で行わない。                                 |
| **`viewmodel`**                                 | **状態管理と調整**。UIとデータ層を仲介し、非同期実行制御（`safeLaunch`）や利用者コンテキストの同期を担当する。                                               | 「UIに何を今見せるべきか？」「ユーザーの操作を受けて次に行うべき処理は？」     | **ロジックの抱え込み禁止**: 複雑な判定は `logic` へ委譲する。`showError` を直接呼ばず `AppException` をスローする。 |
|                                                 | **画面遷移の判断**。次に遷移すべき先を判断し、`ViewEvent` を発行する。                                                                    | 「（保存成功後などに）次に表示すべき画面はどこか？」                 |                                                                                 |
| **`data/repository`**                           | **データアクセス（永続化）**。DBや外部ストレージへのアクセスを主責務とし、業務判断を持たない。監査ログ記録は「許可された副作用」としてここで完遂する。                                 | 「データをどこに、どう保存し、どう取り出すか？」                   | **業務判断禁止**: データの加工や、ステータスによるフィルタリング等の「判断」をリポジトリ内で持たない。                          |
| **`ui/screens`**                                | **画面のエントリポイント**。WindowSize判定、ViewModelの管理、および**画面遷移の実行**を担当。`ViewEvent` を受けて `navController.navigate()` を実行する。 | 「どのViewModelを使い、どのデバイス用レイアウトを表示するか？」       | **詳細レイアウト禁止**: 具体的な `Column` や `Row` の構築は `Content` や `components` に委譲する。       |
| **`ui/components`**                             | **再利用可能な部品**。StatelessなUIパーツ。自身ではデータを保持せず、引数として受け取ったデータとコールバックで動作する。                                           | 「受け取ったデータを、画面上のどの位置に, どの形状で配置するか？」         | **ViewModel依存禁止**: 常に `Stateless` であること。リポジトリや ViewModel への直接アクセスを禁止する。         |
| **`ui/mapping`**                                | **表示表現への翻訳（口）**。Enum等の事実をリソースID（言葉）へ翻訳する。また、グラフ境界線などの「UIとしてのカタログ（構成）」を定義する。                                    | 「この事実（Enum）を、ユーザーに何という言葉（日本語）で伝えるか？」       | **判断ロジック禁止**: 「何が警告（深刻度）か」の判定基準を持たせない。**色の決定（Themeの参照）も行わない。**                  |
| **`theme`**                                     | **視覚的表現（顔色）**。`HealthAlertLevel` などの抽象的な意味に対し、現在のテーマに最適な具体的「色」を割り当てる。                                          | 「深刻度（ALERT等）を、現在のテーマの何色で表現すべきか？」           | **業務知識の禁止**: データの数値（閾値）や文字列（strings.xml）を直接参照しない。                               |

### 1.3.1. 開発の標準手順（ワークフロー）

新機能や新しいカテゴリの画面を追加する際は、以下の順序で検討・実装を進めることを推奨します。これにより、各レイヤーの責務が自然に分離され、手戻りを最小限に抑えられます。

1.  **仕様と事実の定義 (`spec`, `logic/common`)**
    *   `AppSpecifications` にビジネスルール（閾値、最大文字数など）を定義する。
    *   `logic/common` に、状態を表す Enum（例：`Status`）と、それを判定する純粋ロジックを定義する。
2.  **表示カタログの構成 (`ui/mapping`, `theme`)**
    *   `ui/mapping` にて、定義した Enum をどのリソース ID（言葉）に翻訳するかを定義する。
    *   必要に応じて `theme` (HealthAlertColor 等) を拡張し、深刻度に応じた色のマッピングを確認する。
3.  **データ層の実装 (`entity`, `repository`)**
    *   データベースのテーブル定義（Entity）を作成し、Room の DAO と Repository を実装する。
4.  **UIロジックとバリデーション (`logic/feature`)**
    *   画面の入力状態を表す `UiState` データクラスを定義する。
    *   `logic/feature` にて、State から Entity への変換や、保存前のバリデーションロジックを実装する。
5.  **状態管理の構築 (`viewmodel`)**
    *   `BaseUiStateViewModel` を継承し、Repository の呼び出し、非同期制御（`safeLaunch`）、UIイベントの発行を実装する。
6.  **UIコンポーネントの実装 (`ui/components`, `ui/screens`)**
    *   `ui/components` にて、`UiState` を受け取って表示する Stateless な部品を作成し、プレビューを義務化する。
    *   `ui/screens` にて、ViewModel と Component を結合し、ViewModel から送出される `ViewEvent` を購読して `navController` による遷移を実行する。

# 2. 開発の基本指針

- **既存コードとの一貫性の優先**
  - 本プロジェクトでは「一般的なベストプラクティス」よりも、**既存コードとの一貫性を最優先**します。
  - すでに同様の実装（構造、命名、パターン）が存在する場合は、新しい手法を導入せず、既存の設計・命名規則・責務分割を忠実に踏襲してください。
  - 修正時は、対象ファイルだけでなく、**同じ責務を持つ他画面（health, condition, medication 等）も参照**し、プロジェクト内で最も一般的かつ洗練されている実装パターンに合わせてください。
- **影響範囲の最小化**
  - 依頼された修正内容以外について、設計変更やファイル整理を行わない。
- **既存設計とUI/UXの尊重**
  - 既存の設計思想、フォルダ構成、および既存のUI/UXを維持する。
  - 既存実装と異なる設計を採用したい場合は、必ず修正前に理由・メリット・影響範囲を説明し、承認を得ること。
- **不要なリファクタリングの禁止**
  - 「将来のため」「フォルダ構成のみ」「命名変更のみ」といった理由での修正は行わない。
  - 改善案（設計変更を含む）がある場合は、コードを直接修正せず、必ず「改善提案」として提示し、承認を得るまで実装しないこと。
- **コーディング規約の段階的適用（低重要度項目）**
  - 既存コードにおける低重要度の規約違反（`Modifier`の欠落、`collectAsState`の未置換等）については、一括での一斉リファクタリングは行わず、**新規作成時または該当ファイルの改修時にあわせて順次適用**すること。これにより、修正によるデグレードのリスクを最小限に抑えつつ、中長期的にコード品質を向上させる。
- **報告と動作確認**
  - 修正完了時は「修正内容（修正ファイル・共通部品への影響）」「**あえて変更しなかった箇所（影響が懸念されるが意図的に維持した既存挙動など）**」「動作確認が必要な画面」を詳細に報告すること。

# 3. アーキテクチャと実装パターン

## 3.1. 共通部品の扱い

- 本プロジェクトでは、複数の画面で共有される部品を「共通部品」として管理しています。
- 共通部品を変更する際は、影響範囲が広いため、必ず以下の手順で確認を行ってください。
  - **影響範囲の特定**: doc/project_structure.mdの「Components - Screen 逆引きリファレンス」を参照し、🔴マークが付いている部品か、どの画面で使用されているかを確認すること。
  - **動作確認**: チェックがついているすべての画面において、表示崩れやデグレードが発生していないか確認すること。

## 3.2. 定数・ビジネスルールの集約（AppSpecifications / spec）

アプリ全体のビジネスルール（閾値）、入力制限、およびUI制約のための定数は、個別の Composable や ViewModel に分散させず、**`data/AppSpecifications` および `data/spec` 配下を「プロジェクトの辞書」として一元管理**してください。

- **入力制限（数値・文字数）**: 数値入力の整数部・小数部の最大桁数（`DIGITS_...`）や、テキストの最大文字数などはここに定義し、UI（maxLength等）とバリデーションの両方で参照します。
- **ビジネスルールの閾値**: 健康データ（血圧、血糖値等）の判定基準となる数値。
- **UI・システム制約**: 最大写真枚数やページングのサイズなど、アプリの挙動を規定する定数。
- **ロジックの分離**: これらの定数定義には計算式や条件分岐を含めないでください。実際の判定ロジック（`isValid` や `AlertLevel` の決定など）は `logic` レイヤーに記述し、ここで定義された定数を参照する構成を徹底してください（詳細は「1.3. レイヤー別責務定義」を参照）。

## 3.3. 状態管理とパフォーマンス

### 3.3.1. UI状態の初期化とブランキング抑制

#### 3.3.1.1. 基本ルール
- **使い分けの徹底**: `LaunchedEffect` は「一過性のイベント購読」や「副作用の実行」には不可欠ですが、**「状態（初期値）のセット」に使用してはなりません。**
- IDに基づく編集画面・入力画面において、初期値のセットに `LaunchedEffect` を使用することを禁止します。
- 第一選択: 編集対象の状態は ViewModel が保持し、Composable はその状態を表示・更新すること。
- 簡易入力や一時的なUI状態 に限り、remember(key) による初期化を許可する。
- derivedStateOf は変更検知や入力可否などの派生状態の算出に使用し、初期値設定には使用しない。
- 理由: LaunchedEffect による初期化は非同期で実行されるため、初回表示時のブランキング（チラつき）の原因となる。

#### 3.3.1.2. 状態保持の安定性（Key の管理）
- **`remember` の鍵（Key）の安定性**: 入力中に動的に変化する値（例：`editInput.recordTime`）を、入力フィールドの内部状態を保持する `remember` の鍵に使用してはなりません。
- 理由: 鍵が入力のたびに変動するとコンポーネントが強制リセットされ、入力途中のデータ消失や、ViewModel からの逆流による無限補完（「1」が「01」に書き戻される等）の原因となるため。
- 対策: 日時入力などを安定させるため、`UiState` には「入力中の値」とは別に、**「編集セッション開始時の固定時刻（`initialRecordTime`）」**などを保持し、それを `remember` の鍵として使用すること。

#### 3.3.1.3. 実装パターン
- **パターン(1)：ViewModel による状態管理（推奨）**
  - 編集対象のデータは ViewModel 内で `MutableStateFlow` や `mutableStateOf` として保持する。
  - Composable はこれらを直接参照し、イベント（`onValueChange`）で ViewModel を更新する。
  - **用途**: 主要な入力画面（利用者編集、記録入力、設定等）。
- **パターン(2)：`remember(key)` による即時初期化**
  - ViewModel を介さない一時的な状態や、引数の変更に即座に追従すべき状態に使用する。
  - `val state = remember(key) { mutableStateOf(初期値) }` の形式を徹底する。
  - **用途**: ダイアログ内の一時入力、検索フィルタ等。
  - **例外**: `AppTextField` 等の低レイヤー共通部品において、IME状態やカーソル位置の保持が最優先される場合は、内部状態との同期に `LaunchedEffect` を使用することを許容する（日本語入力の堅牢性維持のため）。
- **パターン(3)：`LaunchedEffect` は「アクション」に限定（推奨される用途）**
  - **正当な用途**: スナックバー表示、ナビゲーション、UI通知イベント（`ViewEvent`）の購読、初回表示時のログ記録など、**「副作用（Side Effect）を伴うアクション」**にのみ使用してください。
  - **禁止（アンチパターン）**: `LaunchedEffect` 内で UI ローカルな `mutableStateOf` を書き換えて初期値をセットしたり、手動で ViewModel のロード処理をキックする行為（これらは初回表示時のチラつきの原因となります）。

### 3.3.2. 入力データの保護（破棄確認の必須化）
- **原則**: 文字列入力（名前、メモ等）を伴う「新規作成」および「編集」画面・パネルにおいては、未保存の変更がある状態で「戻る」操作（システム戻るボタン、画面上のキャンセル/戻るボタン）を行った際、必ず**破棄確認ダイアログ**を表示すること。
- **実装**: `BackHandler` および `derivedStateOf` による変更検知（`isChanged`）を組み合わせて実装する。
- **例外**: 「服薬管理」のカレンダー入力など、誤操作のリスクが低い選択主体の入力、またはデータが極めて軽量な場合は、この限りではない。

### 3.3.3. リストデータの安定化と不変性の強制
- ViewModel から取得したリストを Composable 内で加工（フィルタリング等）して子コンポーネントに渡す際は、インスタンスを安定化させ、不必要な再計算を防ぐ。
- **UI 境界における不変コレクション (ImmutableList) の強制**:
  - Compose の再コンポーズ最適化（安定性の保証）を確実に受けるため、**UI 境界（UiState および Composable の引数）においては、原則として `ImmutableList` を使用**すること。
  - 一方、Repository 層や Logic 層（Pure Kotlin 部分）では標準の `List` を使用し、ViewModel が UI 状態を構築する際に `.toImmutableList()` で変換する運用とする。これにより、不要なライブラリ依存の拡散と過剰な変換処理を抑制する。
- **使い分け**:
  - **`derivedStateOf`（Composable 局所最適化）**:
    - **用途**: スクロール位置の監視や、複数の `UiState` フィールドに依存する「表示専用の切り替え」など、再コンポーズ回数を抑制したい場合に使用する。
    - **注意**: ビジネスロジックを伴う判定（例：保存の可否）には使用せず、それは `UiState` 側で保持すること。
  - **`remember(records)`**: `filter` や `map` による新しいリスト生成を伴う場合に利用し、参照の同一性を維持する。加工結果は `.toImmutableList()` で不変型に変換すること。
- **キーの指定**: `remember` のキーには、Flow 等から取得した最新のソースリストを指定すること。
- **理由**: 再コンポーズのたびに新しいリストインスタンスが生成されたり、型が不安定とみなされたりすると、子コンポーネントの不要な再計算やスクロール位置のリセットを引き起こすため。
 
### 3.3.4. SavedStateHandle の適正利用（引数と状態の分離）

- **原則**: `SavedStateHandle` は、画面の初期化に必要な「引数」と、プロセス再生成後にも復元が必要な「最小限の状態」に限定して使用してください。
- **(1) Navigation 引数（外部由来）**:
  - `personId` や `recordId` などの遷移引数は、Navigation ライブラリにより自動的に `SavedStateHandle` へ格納されます。
  - ViewModel はこれを用いて自律的にデータロードを開始します。
- **(2) プロセス再生成用状態（内部由来）**:
  - システムによるプロセス終了（写真撮影からの復帰やメモリ不足時）をまたいで維持すべき「ユーザーの操作状態」のみを保存します。
  - **対象例**: 選択中のタブインデックス、未保存のトグル状態、スクロール位置を決定するIDなど。
  - **非対象例**: DB から再取得可能なエンティティ、大容量のリストデータ、Bitmap 等。
- **(3) UiState との同期（真実のソースの定義）**:
  - **役割分担**: ViewModel 内部の状態管理において、UI が参照する「真実のソース」は常に **`UiState`** です。`SavedStateHandle` はあくまでプロセス再生成に備えた「永続化ストレージ」として位置づけます。
  - **二重管理の禁止**: 同じ値に対して、`UiState` と `SavedStateHandle` を個別に手動更新してはなりません。
  - **同期パターン**: UI からの入力時は `SavedStateHandle[key] = value` の形式で保存（書き込み）を行い、ViewModel 内で `SavedStateHandle.getStateFlow` を購読して、その変更を原子的に `UiState` へ反映させる構成を推奨します。
- **理由**: `SavedStateHandle` (Binder) には容量制限があり、肥大化するとアプリのクラッシュ（TransactionTooLargeException）を招くためです。また、同期を自動化することで、不整合によるバグを構造的に排除します。
 

## 3.4. 利用者コンテキストの確実な切り替え

異なる利用者間での画面遷移や、画面内でのカテゴリ切り替えにおいて、古いデータの残存やローディングのハングを防ぐため、以下の実装を徹底してください。

### 3.4.1. ViewModel でのロード制御
- **即時クリア**: `loadPerson(id)` の開始時に `updateUiState { it.copy(person = null, ...) }` 等を行い、UiState 内のデータを明示的に消去する（`onPrepareLoadPerson` のオーバーライドによるリセットを推奨）。
- **ロードのガードと初回実行の保証**: 無駄なリロードを避けるために `personId` の一致チェックを行う際は、**「ロード処理（Job）が既に一度以上開始されているか」**を併せて判定すること（例：`if (id == currentId && loadJob != null) return`）。単なる ID の一致判定だけでは、初期化処理で ID が先入れされた場合に、初回ロード（DB購読）そのものがスキップされる不具合を招く。
- **Flow監視の自動制御**: データのロード（継続的な監視）は **`flatMapLatest` を第一選択**とし、上流（IDや検索条件等）の変更に伴う古い Flow の自動キャンセルを徹底する。
- **単発Jobの排他制御**: データの保存、同期、一過性の取得などの「単発処理」に限り、`Job` 変数で手動管理を行い、重複実行の防止や適切なタイミングでのキャンセル（`cancel()`）を担保する。基盤機能（`safeLaunch` 等）を用いた実行制御の詳細は第4章を参照。

### 3.4.2. Screen (Composable) でのイベント監視
- **遷移イベントの購読**: `LaunchedEffect(Unit)` を使用し、ViewModel から送出される `viewEvent` を監視します。**イベントの購読は Compose のライフサイクルに応じた副作用であるため、`LaunchedEffect` を用いるのが標準的な実装です。** 遷移ロジック（`navController.navigate`）はこのブロック内でのみ実行し、Composable 内に直接記述しないようにします。
- **再生成後の状態復元**: 写真撮影や外部アプリからの復帰時に「ユーザーの操作コンテキスト」が失われないよう、重要な選択状態などは `SavedStateHandle` を用いて復元可能な構成にしてください（詳細は 3.3.4 項参照）。

## 3.5. Logic レイヤーによる責務の分離

ViewModel の肥大化を防ぎ、テストの信頼性を高めるため、計算や判定のロジックを `logic` レイヤー（Pure Kotlin クラス）に抽出します。

### 3.5.1. ロジック抽出の基準
以下のいずれかに該当する場合は、ViewModel から Logic クラスへの抽出を検討してください。
- **複雑な判定**: ユニットテストで複数の条件分岐（if/when）を網羅する必要があるロジック。
- **純粋な計算・変換**: 西暦/和暦変換や、BMI計算など、入力値から特定の値を導き出す処理。
- **Entity 生成**: 画面の入力状態（UiState）からデータベース保存用クラス（Entity）への詰め替え処理。
- **再利用性**: 複数の ViewModel で共有される可能性がある計算ルール。

### 3.5.2. 実装ルールと禁止事項
- **Pure Kotlin の徹底と Android 依存の排除**:
  - 原則として **Pure Kotlin** で実装し、`Context`, `Uri`, `ContentResolver`, `LiveData/Flow` などの Android API、および Repository 依存を持たない。
  - **抽象化による回避**: 画像処理やファイル操作などで Android API が不可避な場合は、`interface` 等でロジックを抽象化し、実際の Android 依存の実装は Logic レイヤーの外側（`utils` パッケージや `viewmodel` からの注入）に配置すること。
- **標準コレクションの利用**: Logic レイヤー（特に `logic/common` 等）では、特定の UI ライブラリへの依存を避けるため、戻り値には標準의 `List` を使用してよい。UI 層での最適化が必要な場合は、ViewModel 側で不変型へ変換する。
- **副作用の禁止**: Logic クラス内で `MutableStateFlow` を更新したり、Toast を表示したりしてはならない。
- **依存性の排除 (JUnit 高速化)**: Android 依存を排除することで、実機不要な JUnit による高速な単体テストを可能にする。依存が不可避な場合は `mock` 等で差し替え可能な設計を徹底すること。
- **役割の分離**: ViewModel が「状態(State)の管理」を担当し、Logic が「ルールの判定(Calculation/Validation/Conversion/Entity生成)」を担当する。
- **引数と戻り値の明確化**: 入力はプリミティブ型またはデータクラスとし、結果を戻り値として返す「関数型」のスタイルを基本とする。

## 3.6. プラットフォーム機能（OS UI）との連携と責務の委譲

- **目的**: 実機における動作の安定性（ウィンドウフォーカスやライフサイクルの不整合の回避）と開発効率を両立するため、プラットフォーム固有機能の実行場所を以下のように定義します。
### 3.6.1. 実行場所の判定基準

機能の性質に応じて、Composable 内で完結させるか、Activity へ委譲するかを決定します。

| 機能カテゴリ                                 | 実行場所                  | 備考                                                            |
|:---------------------------------------|:----------------------|:--------------------------------------------------------------|
| **ActivityResult API** (カメラ・画像/ファイル選択) | **Composable (起動のみ)** | `rememberLauncherForActivityResult` 等を使用。**結果の処理は後述のルールに従う。** |
| **生体認証** (BiometricPrompt)             | **Activity へ委譲**      | ウィンドウフォーカスやダイアログのライフサイクル管理を集約するため。                            |
| **ランタイム権限要求** (Permission)             | **Activity へ委譲**      | 複数箇所からの要求や、拒否時のシステムダイアログ制御を安定させるため。                           |
| **Window/ライフサイクル依存処理**                 | **Activity へ委譲**      | 画面回転や背景移行時の動作安定性を最優先する処理。                                     |
| **複数画面で共有する OS 連携**                    | **Activity/上位 UI 層**  | 重複実装を避け、一貫した挙動を担保するため。                                        |

#### 運用の詳細ルール
1. **単純な ActivityResult API の許容**: Compose のライフサイクルに安全に統合できる単純な `ActivityResult API` については、`rememberLauncherForActivityResult()` を Composable 内で使用することを許可します。
2. **結果処理の委譲**: ActivityResult の結果（Uri や Bitmap 等）を受け取った後の**業務ロジック、状態管理、データ保存、および画面遷移の判断**については、Composable 内で完結させず、必ず ViewModel または上位 UI 層へ処理を委譲してください。
3. **生体認証の厳格な委譲**: `BiometricPrompt` については、例外なく Activity 側へ処理を委譲します（Composable 内での直接利用は禁止）。

### 3.6.2. 実装パターン
- **委譲対象（認証・権限等）**: 呼び出し元の Activity から処理用の関数（ラムダ）を注入し、Composable はその関数を呼び出すのみとします。
- **Compose 起動対象（ActivityResult 等）**: Composable 内で `rememberLauncherForActivityResult` を定義し、直接結果を受け取りますが、その後の処理は ViewModel へ委譲します。
- 認証成功後に継続する処理は、成功時コールバックとして Composable から渡す。
- デバイスが認証可能かどうかの判定（canAuthenticate() など）は、Activity 側で一元的に管理する。
- この構成により、ウィンドウ管理やライフサイクル管理を Activity に集約し、ダイアログの重なりや Context の不整合による不具合を防止する。

### 3.6.3. 適用対象
以下のような OS 標準 UI を利用する機能は、本ルールを適用する。

- 生体認証（BiometricPrompt）
- ActivityResult API を利用する機能（カメラ起動、ギャラリー・ファイル選択など）
- 通知権限・位置情報権限などのランタイム権限要求
- その他、Activity や Fragment のライフサイクルに依存する OS 標準 UI

## 3.7. 健康記録プロセッサ基盤による多態性の活用 (Processor Pattern)

- **目的**: 身長体重・バイタル・血糖値など、複数の記録カテゴリを共通のフロー（一括入力、共通保存処理等）で扱う際、巨大な `when` 分岐による保守性の低下を防ぎ、カテゴリ追加に対する拡張性を高めます。

### 3.7.1. プロセッサの責務と抽象化
- 複数のカテゴリを横断的に扱うロジック（`BatchInputLogic`, `BatchInputViewModel`, `PersonHealthViewModel` 等）では、具体的な型判定を行わず、必ず **`HealthCategoryProcessor`** インターフェースを介して抽象的に操作してください。
- **プロセッサが担う主要な責務**:
    - **バリデーション**: カテゴリ固有の入力値チェック（範囲、形式）。
    - **Entity 生成**: `UiState` または入力値マップ（`Map<String, Any?>`）からドメインモデル（`HistoryRecord`）への変換。
    - **重複チェック**: 同一日時の既存データの検索。
    - **データ永続化の仲介**: `HealthRepository` の具体的な保存・削除メソッドの呼び出し。

### 3.7.2. 実装および拡張のルール
- **ViewModel からの直接呼び出し制限**: ViewModel は、カテゴリ固有のリポジトリメソッド（`insertHeightAndWeight` 等）を直接呼び出さず、プロセッサの `save()` / `delete()` メソッドに処理を委譲してください。これにより、ViewModel は「指揮官（フロー制御）」としての役割に専念できます。
- **レジストリによる集中管理**: 新しい記録カテゴリを追加する場合は、`HealthCategoryProcessor` を実装した新しいクラスを作成し、**`HealthProcessorRegistry`** に登録してください。この手順により、既存の ViewModel や Logic のコードを一切修正することなく、新機能の統合が可能になります。
- **一貫したエラー翻訳**: 各プロセッサに `categoryNameResId` や `outOfRangeErrorResId` を定義し、ViewModel 側での動的なメッセージ構築を可能にすることで、カテゴリを問わず一貫したユーザー通知を保証してください。

# 4. エラーハンドリングと実行制御 (safeLaunch / safeCollect)

予期せぬエラー発生時もユーザーが迷わず、かつシステムの状態が確実に復帰するよう、`BaseUiStateViewModel` の基盤機能を活用した実装を徹底してください。

## 4.1. 基盤機能の利用原則
- **非同期実行制御**: 全ての ViewModel は `BaseUiStateViewModel` を継承し、`safeLaunch` / `safeCollect` を使用して非同期処理を開始する。`viewModelScope.launch { ... }` の直接使用は原則禁止。
- **Repository の責務**: Repository は業務判断（ステータスによるフィルタリング等）を持たず、データアクセスと例外の再スローに専念する。ただし、データの変更を伴う操作における監査ログの記録は、Repository の正当な副作用として許容される。
- **通知の委譲**: 異常系（エラー）発生時は、ブロック内で `showError` を直接呼ばず、適切な `AppException` をスローして基盤側に通知とログ記録を委譲する。
- **正常系通知**: 保存完了等の正常な通知には `showSnackbar` を利用する。
- **共有コンテキスト**: `PersonDetailUiStateViewModel` は、詳細画面群 (A)(B)(C) で共有される利用者情報の保持と共通ヘッダーの制御を担当する。
- **ローディング状態の自動制御**: `safeLaunch` 等の `loadingState` 引数を利用し、開始・終了のフラグ更新を基盤側に委譲する。手動でのフラグ操作（漏れの原因）を避けること。
- **手動 try-catch の制限**: ViewModel 内に生の `try-catch` を記述するのは、複雑な合成 Flow や特殊なリトライ処理など、基盤機能では表現できない特殊ケースのみとする。
- **CancellationException**: 基盤側で自動的に再スローされるため、ViewModel 側で個別にキャッチや判定をする必要はない。
- **正常終了後の UI 操作**: 画面遷移やダイアログの閉鎖などの UI 操作（`sendViewEvent` 等）は、`safeLaunch` ブロック内の**最終行**で行う。ブロック内で例外が発生した場合はこれらの処理は実行（到達）されないため、処理の原子性が保たれる。

## 4.2. 責務の分割

各レイヤーの役割を以下のように定義し、エラーハンドリングの連鎖（事実から通知へ）を構成します。

| レイヤー           | 主要な役割         | エラー発生時の振る舞い                                        |
|:---------------|:--------------|:---------------------------------------------------|
| **Repository** | **データアクセス**   | 業務判断を持たず、低レイヤーの例外を「再スロー」する。操作履歴（ログ）の記録を担う。         |
| **Logic**      | **業務ルール**の判定  | 「事実（理由）」を Enum 等で返す。契約違反（前提条件不備）は標準例外を投げる。         |
| **ViewModel**  | **UI判断**と状態管理 | 事実を UIリソース（R.string）に翻訳し、`AppException` を生成・スローする。 |
| **Handler**    | **通知**と記録（基盤） | `AppException` を受け取り、ダイアログ表示と監査ログ記録を自動で完遂する。       |

## 4.3. Logic / Utility レイヤーにおけるエラー設計

Logic レイヤーの純粋性（Pure Kotlin）と、ViewModel による適切な通知を両立させるためのルールです。

- **Logic の純粋性**: Logic は UI リソース（`R.string`）や `AppException`（ViewModel層のクラス）に依存してはならない。
- **役割の分離（事実と通知）**:
  - **Logic (事実 of 定義)**: 判定を行い、その「事実（理由）」を返す。失敗理由が複数ある場合は `Boolean` ではなく **`enum class` や `sealed interface`** など、理由を詳細に識別可能な型を戻り値として使用する。
  - **ViewModel (通知への翻訳)**: Logic から返された事実に基づき、適切なリソースIDを選択して `AppException` をスローする。
- **例外の伝播（低レイヤー）**: `ImageUtils`, `ZipUtils` 等の低レイヤー部品で発生したシステム的な失敗（`IOException` 等）は、内部で握りつぶさず、そのままスローして ViewModel に判断を委ねる。
- **標準例外 of 活用**: Logic of 契約（前提条件）違反を検知した場合は、`IllegalArgumentException` や `IllegalStateException` をスローして良い。これらは回復不能なプログラミング上の誤りとして扱い、ViewModel of ハンドラで `VALIDATION_ERROR` 等として自動処理される。

## 4.4. 通知と例外のスロー (AppException)
UI通知が必要なエラーについては、以下のルールに従い `AppException` を活用します。

- **ViewModel の責務（翻訳）**: **`AppException` は、Logic が返した業務上の判定結果や、下位レイヤーから伝播した例外を、UI通知へ変換するために ViewModel が生成する。**
- **手動 showError の禁止**: `safeLaunch` ブロック内において、直接 `showError` を呼び出してはならない。
- **AppException のスロー**: タイトルやメッセージのリソースIDを保持できる `AppException`（および `AppValidationException`, `AppIOException`）をスローすることで、基盤に通知を委譲する。
- **自動ハンドリング**: 基底クラス側で例外の型に基づき、`resultType`（`IO_ERROR`, `VALIDATION_ERROR` 等）の判別と、適切なダイアログ表示が自動的に行われる。

### 4.4.1. AppException の継承階層
ViewModel がスローする通知用例外は、以下の構造で定義・使用すること。

```
AppException
├── AppValidationException (バリデーション失敗・業務ルール違反)
├── AppIOException (ファイル入出力・接続エラー)
├── AppDataException (データ整合性・DBエラー)
├── AppExternalException (外部アプリ連携エラー)
└── AppSecurityException (生体認証・権限エラー)
```

## 4.5. 通知の使い分け
- **致命的・要対話エラー (AppException)**: ユーザーへの通知が必要な異常系。適切な情報を保持させた `AppException` をスローし、基盤（Handler）を介してダイアログで通知する。
- **正常系通知 (showSnackbar)**: **例外ではない正常な完了通知専用**とする。保存完了、削除完了、コピー完了、設定変更の適用など、ユーザーの操作が成功したことを知らせるために使用する。

# 5. UI 状態（UiState）の集約と原子性の確保

## 5.1. 目的
- UI状態管理を UiState に統一し、状態更新の原子性を確保する。

## 5.2. 具体的ルール

- **1画面 1UiState**:
  - 画面が表示に必要とする状態は、原則として一つの UiState データクラスに集約する。
  - 例：`loading`, `error`, `data`, `selectedItem` , `dialog表示状態`, `isValid`, `その他UI表示に必要な状態`等
- **不変コレクションの強制**:
  - UiState 内のリスト型プロパティには必ず `ImmutableList` を使用すること。標準の `List` を使用した場合は再コンポーズ最適化の対象外となるため禁止とする。
- **リソース ID への文言集約**:
  - ユーザー向けの固定文言（ラベル、メッセージ、アクセシビリティ用説明文等）はすべて `strings.xml` に集約し、コード内への日本語のハードコードを禁止する（詳細は第11章を参照）。
- **原子的な更新**:
  - UiState の変更は、原則として `_uiState.update { it.copy(...) }` のみで行う。
  - 複数の MutableStateFlow を個別更新し、一時的に矛盾した状態をUIへ通知してはならない。
- **派生状態の定義（責務による使い分け）**:
  - **UiState に含めるべきもの**:
    - **「ロジック・業務上の判定結果」**（例：`isValid`, `isSaveEnabled`, 合計値など）。
    - ViewModel で計算し、Unit Test の検証対象となるもの。
  - **Composable で `derivedStateOf` 等を用いるもの**:
    - **「表示・演出上の派生値」**（例：スクロール位置に応じた表示の有無、ローカルなフォーカス状態に基づく表示変更）。
    - ViewModel が知る必要のない、UI 内部の最適化のための状態。
  - `combine()`の利用ルールを次の通りとする。
    - **禁止**：
      - MutableStateFlow 同士を combine() して UiState を構成すること。
      - UiState の各プロパティを combine() に依存して維持すること
    - **許可**：
      - Repository 等の複数の外部 Flow を同期すること。
      - 同期した結果を 1 回の `_uiState.update { ... }` で反映すること。
      - Repository等から取得するデータそのものを合成する用途まで禁止するものではありません。
- **状態の分類**：状態は次の2種類を区別する。
  - **保存すべき状態**：UIが保持する値、編集中データ、選択状態、ダイアログ状態、エラー状態
  - **毎回計算すべき値**：一時的な表示用の値、単純な算出結果、保持不要な派生値
  - 保持不要な値まで UiState に保存しない。
- **型安全な状態とイベント**: ジェネリクスを用い、画面ごとの `UiState` (S) と `ViewEvent` (E) を適切に管理する。
- **安全なローディング制御**:
  - 基盤の `loadingStateProxy` を通じて `UiState.isLoading` を自動更新させる。
  - ViewModel 内で `isLoading = true` といったプロパティへの直接代入（個別更新）を行わない。

# 6. テスト・品質保証ルール

「動くコード」だけでなく「壊れないコード」を維持するため、以下のテスト戦略を遵守してください。

- **プレビューの義務化：** すべての `*Content.kt` および主要な `Components` にには、**「正常系」「空状態」「エラー/注意状態」**を網羅する 1 つ以上の `@Preview` を含めること。
- **PreviewParameterProvider の積極活用：** 複数の状態を網羅する際や、複雑なデータ構造を持つ Composable のプレビューでは `PreviewParameterProvider` を使用し、プレビュー関数の肥大化を防ぎつつ網羅性を担保すること。
- **テストの作成・更新：** 新規機能追加や大規模な修正時は、`doc/test/project_TEST_GUIDELINES.md` に基づき、Logic Test (JUnit) と UI Test (ComposeTestRule) をセットで更新し、デグレードを防止すること。基底クラスの変更時は `BaseUiStateViewModelTest.kt` も確認すること。
- **テスト容易性の確保：** ViewModel や Repository を Composable に直接渡さず、Stateless な Content 層を設けることで、プレビューおよびコンポーネントテストの容易性を維持すること。

テスト・プログラムを作成する際は、以下のルールとします。

- **仕様書の作成**：
  - 冒頭に**対象テストコード**を明記
  - 各テスト仕様にはIDを必ずつける
  - テスト用タグをつけた場合はその内容を明記
- **テストプログラムの作成**：
  - 関数名には冒頭にテスト仕様書のIDを接頭語として必ずつける
  - 関数名に日本語は用いない
  - 仕様書に記載のテスト仕様(ID)に対し漏れがないことを確認する

# 7. セキュリティ・バイ・デフォルト

CareMemo では、ユーザーの操作なしに「デフォルトで最も安全な状態」が提供されるよう、以下の設計指針を遵守してください。

- **重要操作の保護（生体認証）**: セキュリティ設定の変更やデータのバックアップ/復元などの破壊的または広範囲な操作には、生体認証または端末ロック解除を必須とします。

# 8. 操作ログ (監査ログ) の実装

アプリの透明性と保守性を高めるため、データの変更を伴う操作（CRUD）および**重大なエラー**については必ず操作ログを記録します。

## 8.1. 識別子の管理ルール
ログの検索性と一貫性を保つため、以下のルールに従って名称を定義します。

- **tableName (テーブル名)**: プロジェクト共通の定数として管理することを推奨。
- **featureName (機能名)**: 各 ViewModel で `companion object` 定数を定義し、`abstract val featureName` をオーバーライドしてそれを返す。
- **operation (操作名)**: 各 ViewModel 内で `private const val OP_...` として定義する。

## 8.2. ログ記録のフロー
- **正常操作**: Repository のメソッド内で、ViewModel から渡された `featureName`, `operation` を用いて記録する。
- **エラー（ERROR）記録**: `safeLaunch` / `safeCollect` の `contextBuilder` で情報を指定し、ハンドラを介して自動的に記録する。**`resultType` は、発生した例外の型に応じて自動的に決定される。**

## 8.3 実装上の注意点
- **例外処理**: ログ記録自体が失敗しても、本来の業務処理を妨げないこと（基盤側で考慮済）。
- **actionType**: 原則として `INSERT`, `UPDATE`, `DELETE`, `LOGICAL_DELETE`, `RESTORE`, **`ERROR`** を使用する。
- **個人情報の保護**: `details` には氏名等の個人情報を直接含めず、IDのみを記録するかマスキングを適用すること。

# 9. 画面遷移 (NAV) ルール（Type-safe Navigation, SavedStateHandle, ViewEvent 一元化）

本プロジェクトの画面遷移は、堅牢性とテスタビリティを確保するため、以下の3つの柱に基づいた「Type-safe Navigation, SavedStateHandle, ViewEvent 一元化」構造を徹底します。

- **(1) Type-safe Navigation（目的地）**: 
    - すべての画面（目的地）は、`ui/navigation/Destinations.kt` に `@Serializable` な `object` または `data class` として定義すること。
    - 画面が必要とする「必須データ（引数）」をこの定義に集約し、文字列ベースのルート指定を全廃する。
- **(2) ViewEvent 一元化（トリガー）**:
    - **責務の分離**: 画面遷移は「判断（ViewModel）」と「実行（Screen）」に分離する。
        - **ViewModel（判断）**: 業務ロジックやバリデーション結果に基づき、**「どこへ遷移すべきか」を判断して `ViewEvent` を発行する**。これにより、遷移の妥当性を Unit Test で検証可能にする。
        - **Screen（実行）**: `LaunchedEffect(Unit)` 内で **`ViewEvent` を受けて `navController.navigate()` 等の Navigation API を実行する**。
    - **直接遷移の禁止**: Composable（特に Button の `onClick` 等）から直接 `navController.navigate()` を呼び出すことは原則禁止とする。必ず ViewModel を介して遷移の「意図」をイベントとして発行すること。
- **(3) SavedStateHandle（初期化）**:
    - 目的地に到着した際の**引数の受け取り**は、Navigation ライブラリと `SavedStateHandle` の自動連携に一本化する。
    - ViewModel は自ら `SavedStateHandle` から引数を抽出し、自律的にデータロードを開始する。
    - 画面固有の内部状態（選択インデックス等）を保持する場合も、この仕組みを併用するが、保存するデータ量は最小限に留めること。
    - `MainActivity` 内で `savedStateHandle` に対して手動で値をセットしたり、引数を抽出して Composable へ手動で渡したりしないこと。

- **その他の運用ルール**:
    - **Back Stack の遵守**: 本アプリは Android 標準の Back Stack に従う。
    - **遷移の局所化**: 画面遷移は原則として隣接する画面間のみ定義する。
    - **戻る操作の定義**: Android の「戻る」ボタンによる単純な戻りは NAV-ID を定義しないが、「保存成功後に自動で戻る」といった業務シナリオ上重要な遷移については NAV-ID を定義し、ViewEvent 経由で実行する。

# 10. コーディング規約・禁止事項

## 10.1. Modifier の伝播と責務の分離
コンポーネントの再利用性と予測可能性を高めるため、Modifier の扱いについて以下のルールを厳守してください。

- **引数の定義**: 
  - すべての Composable 関数は、原則として `modifier: Modifier = Modifier` を引数に持つこと。
  - `modifier` は、必須引数の直後、かつ最初のオプション引数として配置すること。
- **ルート要素への適用**:
  - 外部から渡された `modifier` は、そのコンポーネントの**最外位（ルート）要素にのみ**適用すること。
  - 内部の子要素に対して外部 `modifier` を使い回したり、複数の要素に分割して適用したりしてはならない。
- **レイアウト責務の分離と二重余白の防止**:
  - `Screen/Phone/Tablet` 層は画面全体のレイアウト（配置・外側余白）を担当し、`Content` 層は受け取った `modifier` をルート要素に適用する責務を負います。
  - **外側余白の原則禁止**: `Content` コンポーネント自身がルート要素に対して追加の `padding()` を持つことは原則禁止とします。固有の余白が必要な場合は、内側の要素に対して個別に指定してください。これにより、上位層と下位層での「二重余白」の発生を構造的に防止します。
  - **既存 Modifier の継承と連鎖**: 上位から渡された `modifier` は、破棄や上書きをせず、必ずルート要素へ適用してください。コンポーネント固有の属性（`background` や内部的に必須な `fillMaxSize` 等）が必要な場合は、渡された `modifier` を起点として連鎖（chain）させて適用します。
  - **外部 Modifier の純粋性維持**: 外部から渡された `modifier` に対して、内部の都合で `padding()`, `fillMaxSize()`, `weight()` などの「呼び出し側が制御すべきレイアウト属性」を勝手に連結してはなりません。呼び出し側の意図を尊重した適用を徹底してください。
- **例外（testTag）**:
  - UIテスト用の `testTag` 付与に限り、外部 `modifier` への連結を許可する。

## 10.2. 不変コレクション (ImmutableList) の強制
Compose の再コンポーズ最適化（安定性の保証）を確実にし、予期せぬサイドエフェクトを防ぐため、コレクションの扱いについて以下のルールを厳守してください。

- **適用範囲（UI 境界）**:
  - **必須箇所**: `UiState` のプロパティ、および Composable 関数の引数。これらは再コンポーズの最適化に直結するため、`ImmutableList<T>` を厳守すること。
  - **任意（推奨しない）箇所**: Repository 層、Entity、およびドメインロジック層。これらは標準の `List` を使用し、UI 層に渡る直前で変換を行う。
- **変換と生成**:
  - ViewModel において、Flow の監視結果や Logic 層の戻り値を `UiState` に反映する際、`.toImmutableList()` を用いて不変型へ変換する。
  - Composable 内部で `filter` や `map` を行った結果を子コンポーネントに渡す場合も、同様に変換を行うこと。
  - 空のリストを初期値として定義する場合は、`persistentListOf()` を使用すること。
- **プレビュー用モックデータの扱い**:
  - プレビューで使用するテストデータは、原則として `ui/preview/MockData.kt` に集約し、各プレビュー関数で個別にハードコードしないこと。
  - 大規模な画面（Screen層）のプレビューでは、引数をまとめた `PreviewState` クラスと `PreviewParameterProvider` を組み合わせ、一貫した状態管理を行うこと。
- **マッピング**:
  - キーと値のペアを扱う場合も、同様の理由から `ImmutableMap<K, V>` および `persistentMapOf()` を使用すること。

## 10.3. その他コーディング規約
- **State収集**: Composable内では `collectAsStateWithLifecycle()` を使用する。
- **エラーハンドリング**: 第4章の指針に従い、`safeLaunch` / `safeCollect` を用いて例外の伝播と適切な通知（`AppException`）を徹底すること。

# 11. リソース管理とタイポグラフィ規約

多言語対応の基盤を維持し、アプリ全体で文言の一貫性と高い視認性を保つためのルールです。

## 11.1. 文言の集約（strings.xml）
- **原則**: ユーザーの目に触れる固定文字列は、すべて `res/values/strings.xml` に定義すること。
- **移行対象外**: 以下の項目は、設計上の理由から例外的にハードコード（または定数定義）を許可する。
    - 内部システム識別子（DBテーブル名、監査ログの `actionType` や `resultType` 等）。
    - テスト用データ（`SampleDataGenerator` 等で使用するダミーの氏名・本文）。
    - システム的なログ出力用のタグや内部的なキー文字列。

## 11.2. リソース ID の命名規則
リソースの検索性と整理のしやすさを保つため、以下の接頭辞を使用すること。

| 接頭辞                  | 用途                       | 例                                     |
|:---------------------|:-------------------------|:--------------------------------------|
| `common_`            | 複数の画面で共有される汎用的なラベルやメッセージ | `common_save`, `common_cancel`        |
| `settings_item_`     | 設定画面の各項目タイトル             | `settings_item_app_lock_title`        |
| `settings_section_`  | 設定画面のセクション見出し            | `settings_section_security`           |
| `settings_dialog_`   | 設定画面で表示されるダイアログ固有の文言     | `settings_dialog_restore_confirm_msg` |
| `health_`, `main_` 等 | 各機能・画面固有の文言              | `health_title`, `main_desc_op_menu`   |

## 11.3. 実装パターン：Mapper とリソース ID
- **Mapper の責務**: `ui/mapping` 配下の各 Mapper クラス（例：`HealthDisplayMapper`）は、原則として **リソース ID (`Int`)** を返すように設計すること。
- **UI での解決**: 文字列の最終的な解決は、UI 層（Composable）で `stringResource(id)` を呼び出す際に行う。
- **理由**: ロジック層やマッパー層に `Context` や具体的な `String` を持ち込まず、多言語対応（`values-en` 等）を透過的にサポートするため。

## 11.4. タイポグラフィと特殊文字
正確で美しい表示を行うため、以下の特殊文字・実体参照を適切に使用すること。

- **著作権表示**: `(C)` ではなく **`&#169;`** (©) を使用する。
- **期間・範囲表示**: ハイフン `-` や波線 `〜` ではなく、原則として **`&#8211;`** (– / en dash) を使用する。
- **省略記号（三点リーダー）**: 文字列としての `...` は使用せず、**`&#8230;`** (…) または全角の `…` を使用して Lint 警告を回避する。
- **プレースホルダ**: 数値や文字列を埋め込む場合は、位置指定子（`%1$d`, `%1$s` 等）を明示的に使用し、翻訳時の語順変更に対応可能にすること。
