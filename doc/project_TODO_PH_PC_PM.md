# PH/PC/PM 系統の実装一貫性に関する調査報告と今後の課題

このドキュメントは、主要3系統（健康記録・所見メモ・服薬管理）の実装における一貫性の現状と、将来的なリファクタリングの指針を記録したものです。

---

## 1. 調査の目的
`project_RULES.md` の「1.2. 詳細画面の設計原則」および「4.2. 責務の分割」に基づき、SCR-PH-001, SCR-PC-001, SCR-PM-001 の3画面が統一的な思想で実装されているかを確認する。

---

## 2. 統一されている点（維持すべき良好な状態）
以下の項目は3系統すべてで完全に一貫しており、CareMemo アーキテクチャの根幹として維持されています。

- **4ファイル構成**: すべて `Screen`, `ScreenPhone`, `ScreenTablet`, `ScreenContent` に役割が分離されている。
- **Dual-ViewModel**: `PersonDetailUiStateViewModel`（共通）と `専門ViewModel` の併用が徹底されている。
- **エラーハンドリング**: `safeLaunch` / `safeCollect` による非同期制御と、Logic層の「事実」を ViewModel で「翻訳（AppException）」してスローするフローが統一されている。
- **利用者同期**: `Screen` 層の `LaunchedEffect(detailState.personId)` によるロードトリガーが共通化されている。

---

## 3. 微細な違いがある点（リファクタリングの検討対象）
実装の「癖」やデータの性質により、以下の点にバリエーションが存在します。

### 3.1. データロードのトリガー（ViewModel内）
- **PH (健康)**: `init` 内で `combine` を用いて ID とカテゴリを監視し、自動ロードする。
- **PC (所見) / PM (服薬)**: `updateWithPersonData`（基底クラスのオーバーライド）でデータ確定時に明示的にロードを開始する。
- **【指針】**: 基底クラスの設計意図に近い PC/PM の方式に統一することで、ライフサイクル管理をよりシンプルにできる可能性がある。

### 3.2. 監査ログのテーブル名定義
- **PH / PM**: `companion object` で定数（`TABLE_...`）を定義している。
- **PC**: `safeCollect` 等の引数にリテラル（`"condition_db"`）を直接記述している箇所がある。
- **【指針】**: `project_RULES.md` 8.1項に基づき、PC も定数管理へ移行すべきである。

### 3.3. 検索機能の有無
- **PC (所見)**: UI（SearchBox）および Logic（filterRecords）が完備されている。
- **PH / PM**: ロジックのみ存在、または UI に露出していない。
- **【指針】**: 記録件数が増加した場合の利便性を考慮し、将来的に PC のパターンを PH/PM にも展開することを検討する。

### 3.4. ナビゲーションパラメータ（検索クエリ）の引き継ぎ
- **PC (所見)**: 一覧画面の検索クエリを URL パラメータとして引き継ぎ、画面内フィルタに反映させている。
- **PH (健康)**: ナビゲーション定義上はクエリパラメータが存在するが、画面側では使用しておらず、業務上の必要性も低い。
- **【指針】**: 数値主体の PH 系統においては、不要な複雑さを避けるためクエリパラメータを削除し、ナビゲーションルートを整理すべきである。
